# Phase 0 — Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up `dispatcharr-easy`'s repo scaffold, lint/format/test tooling, CI, and a fully tested typed-API-client + JWT-auth layer — the foundation every later page (including the Phase 0 Dashboard and app shell) builds on.

**Architecture:** A Vite + React + TypeScript SPA using Mantine 8. A committed, OpenAPI-generated typed client (`openapi-typescript` + `openapi-fetch`) talks to Dispatcharr's REST API over relative `/api/...` URLs — same-origin in production (this app is overlaid into Dispatcharr's own `frontend/dist/`), proxied by Vite in local dev. Auth follows Dispatcharr's existing `rest_framework_simplejwt` flow: access token in memory (Zustand store), refresh token in `localStorage`, a `fetch` override that retries once on 401 after a silent refresh.

**Tech Stack:** Vite 8, React 19, TypeScript (~6.0, template-pinned), Mantine 8, Zustand 5, ESLint 10 (flat config) + Prettier 3, Vitest 4 + React Testing Library 16, `openapi-typescript` 7 + `openapi-fetch` 0.17.

## Global Constraints

- This repo contains **no Dispatcharr source** — no subtree, no submodule, no forked files. It only ever talks to Dispatcharr over its existing public HTTP/WebSocket API.
- This repo is **public and MIT-licensed**. Never commit secrets, credentials, or a specific user's private instance URL into tracked files.
- Stack pins (matching Dispatcharr's own frontend, per the design spec): **Mantine 8** (not 9), **react-router-dom v7**, **Zustand**, **TanStack Table**. This plan only needs Mantine 8 and Zustand; the other two are pulled in by the app-shell/dashboard plan that follows this one.
- Auth: access token held **in memory only** (never persisted); refresh token in `localStorage`; a fetch wrapper retries once on 401 after a silent refresh; redirect-on-refresh-failure is the app shell's job (next plan) — this plan's job is to clear auth state (`logout()`) on refresh failure so the next plan has a clean signal to react to.
- The OpenAPI client is **generated and committed**, not regenerated on every build.
- Mobile-first responsiveness is a later plan's concern (app shell) but nothing in this plan should assume a desktop-only viewport.

- [ ] **Step 4: Implement**

Write `src/auth/authStore.ts`:

```ts
import { create } from 'zustand'

export const REFRESH_TOKEN_KEY = 'dispatcharr-easy:refreshToken'

interface AuthState {
  accessToken: string | null
  isAuthenticated: boolean
  setTokens: (tokens: { access: string; refresh?: string }) => void
  clear: () => void
}

export const useAuthStore = create<AuthState>((set) => ({
  accessToken: null,
  isAuthenticated: false,
  setTokens: ({ access, refresh }) => {
    if (refresh) {
      localStorage.setItem(REFRESH_TOKEN_KEY, refresh)
    }
    set({ accessToken: access, isAuthenticated: true })
  },
  clear: () => {
    localStorage.removeItem(REFRESH_TOKEN_KEY)
    set({ accessToken: null, isAuthenticated: false })
  },
}))

export function getStoredRefreshToken(): string | null {
  return localStorage.getItem(REFRESH_TOKEN_KEY)
}
```

import { useAuthStore, getStoredRefreshToken } from './authStore'

interface TokenPairResponse {
  access: string
  refresh: string
}

interface AccessTokenResponse {
  access: string
}

export async function login(username: string, password: string): Promise<boolean> {
  const response = await fetch('/api/accounts/token/', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ username, password }),
  })
  if (!response.ok) {
    return false
  }
  const tokens = (await response.json()) as TokenPairResponse
  useAuthStore.getState().setTokens(tokens)
  return true
}

let refreshInFlight: Promise<boolean> | null = null

export function refreshAccessToken(): Promise<boolean> {
  if (!refreshInFlight) {
    refreshInFlight = performRefresh().finally(() => {
      refreshInFlight = null
    })
  }
  return refreshInFlight
}

async function performRefresh(): Promise<boolean> {
  const refresh = getStoredRefreshToken()
  if (!refresh) {
    return false
  }
  const response = await fetch('/api/accounts/token/refresh/', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ refresh }),
  })
  if (!response.ok) {
    return false
  }
  const { access } = (await response.json()) as AccessTokenResponse
  useAuthStore.getState().setTokens({ access })
  return true
}

export function logout(): void {
  useAuthStore.getState().clear()
}

Write `src/api/authFetch.ts`:

```ts
import { useAuthStore } from '../auth/authStore'
import { refreshAccessToken, logout } from '../auth/authClient'

export async function authFetch(
  input: RequestInfo | URL,
  init: RequestInit = {},
): Promise<Response> {
  const base = new Request(input, init)

  const response = await fetchWithToken(base.clone())
  if (response.status !== 401) {
    return response
  }

  const refreshed = await refreshAccessToken()
  if (!refreshed) {
    logout()
    return response
  }

  return fetchWithToken(base.clone())
}

function fetchWithToken(request: Request): Promise<Response> {
  const token = useAuthStore.getState().accessToken
  if (token) {
    request.headers.set('Authorization', `Bearer ${token}`)
  }
  return fetch(request)
}
```

`openapi-fetch` (Task 10) calls the injected `fetch` as `fetch(request, requestInitExt)`, where `request`
is already a real `Request` instance carrying all headers (including `Content-Type` for bodied requests)
and `requestInitExt` is `{}`. Constructing `new Request(input, init)` once — the same merge Fetch itself
performs — and then cloning it per attempt is what makes both a bare string URL (`authFetch('/api/...')`,
as `openapi-fetch` never calls it, but tests and callers may) and a real `Request` object work identically,
and what allows the same body to be sent on both the initial attempt and the post-refresh retry without
hitting `TypeError: Cannot construct a Request with a Request object that has already been used`. Mutating
`request.headers` in place (rather than replacing the header set, e.g. via `new Headers(init.headers)`)
preserves whatever headers the caller already set on the `Request`/`init`.
