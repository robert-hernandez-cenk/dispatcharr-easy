# App shell + Dashboard — design

Date: 2026-08-08

## Problem

Phase 0's foundation (repo scaffold, tooling, typed API client, JWT auth layer) is complete and merged. Per the [Phase 0 design spec](2026-08-08-phase0-foundation-design.md), the next slice is the responsive app shell (nav, layout, theming) and the Dashboard/home page — Phase 0's flagship page, proof that build → overlay → auth → real data works end-to-end. There is currently no UI at all: no login screen, no navigation, no page that renders real Dispatcharr data.

## Context gathered from the real instance

Dispatcharr's current UI (checked live, 2026-08-08) has **no Dashboard/home page** — its nav is Channels, VODs, M3U & EPG Manager, TV Guide, DVR, Stats, Plugins, Integrations, System (Users / Logo Manager / Settings). The closest existing thing is the **Stats** page: an "Active Connections" panel (streams / VOD connections / catch-up sessions, live-refreshing) and a collapsible "System Events" log.

Checked against the committed `src/api/schema.d.ts` (generated from this same instance):
- `GET /api/channels/channels/?page_size=1` and `GET /api/channels/streams/?page_size=1` return standard DRF pagination (`{count, next, previous, results}`) — cheap way to get total counts without fetching full lists.
- `GET /api/m3u/accounts/` returns `M3UAccount[]`: `name`, `is_active`, `status` (enum), `last_message`, `updated_at`.
- `GET /api/epg/sources/` returns `EPGSource[]`: `name`, `status` (enum), `last_message`, `updated_at`.
- **No REST endpoint exists for active connections** — the schema (generated by drf-spectacular from real DRF views) has nothing matching "active"/"session"/"connection" outside `/api/catchup/sessions/`. This is WebSocket-only (Django Channels), consistent with the parent spec's "HTTP/WebSocket API" framing. Decision (below): out of scope for this plan.

## Non-goals (this plan)

- **Active connections / live streaming session data.** WebSocket-only, no REST path; would require a new WebSocket client with JWT auth and reconnect handling — real scope beyond what Foundation's HTTP-only auth layer supports. Deferred to whichever later plan first needs live/WebSocket data.
- **Full site navigation.** Nav shows only "Dashboard" (+ user menu / logout) for Phase 0, not placeholder entries for Channels/EPG/VOD/etc. Nav grows one entry per future plan, each of which is free to restructure it as needed.
- **Route-level auth guards.** A single `AuthGate` wrapping the whole app is sufficient for two pages (Login, Dashboard); per-route guards are deferred until there are enough protected routes to justify the machinery.
- Feature parity with Dispatcharr's own Stats/System pages — the Dashboard is a new page, not a port of an existing one.

## Architecture

### Routing & auth gating

`AuthGate` (`src/auth/AuthGate.tsx`) wraps the whole app, replacing route-level guards for now:

1. On mount: if a refresh token exists in `localStorage`, call `refreshAccessToken()` (from Foundation's `authClient.ts`).
2. While pending: render a centered loading state.
3. On success: render the app's router.
4. On failure (or no refresh token at all): render `<Navigate to="/login" />` / render the login route directly.
5. **New wiring vs. Foundation:** `authFetch`'s existing 401→refresh→retry→`logout()`-on-failure behavior changes `useAuthStore`'s `isAuthenticated` out from under the currently-rendered page (e.g. an expired session while sitting on the Dashboard). `AuthGate` subscribes to `isAuthenticated` and redirects to `/login` whenever it flips to `false` after initial mount — this is the one piece of behavior this plan adds on top of Foundation's auth layer.

Router (`react-router-dom` v7): two routes for now — `/` (Dashboard, inside `AuthGate` + `AppLayout`) and `/login` (outside `AppLayout`, no nav). Kept intentionally minimal; later plans add routes without restructuring this.

### Components

- **`AuthGate`** — see above.
- **`LoginPage`** (`src/pages/LoginPage.tsx`) — centered Mantine card, username/password via `@mantine/form`, calls `login()`, inline error on failure (from the response body's `detail`), navigates to `/` on success.
- **`AppLayout`** (`src/components/AppLayout.tsx`) — wraps Mantine's own `AppShell` component: header (app name, color-scheme toggle, user menu with logout) + navbar that collapses to off-canvas below the `sm` breakpoint via a burger icon in the header. Navbar content: "Dashboard" link only. (Named `AppLayout`, not `AppShell`, to avoid colliding with the Mantine component of the same name it wraps.)
- **`DashboardPage`** (`src/pages/DashboardPage.tsx`) — fetches channel count, stream count, M3U accounts, EPG sources in parallel via `apiClient` on mount. Renders a stat-tile row (channel count, stream count; responsive `SimpleGrid`, 2 cols mobile up to 4 desktop) and a source-health section (one card per M3U account / EPG source: name, color-coded status badge, `last_message`, relative `updated_at`).
- **`StatTile`** / **`SourceHealthCard`** — small, presentational, props-only components with no data-fetching of their own; independently testable.

### Data flow & error handling

- `DashboardPage` issues its requests in parallel, tracks one loading state, and is **partial-failure tolerant**: if one request fails (e.g. EPG sources) the rest still render, with a Mantine `Alert` in place of the failed section rather than the whole page failing.
- Other API errors (e.g. login) surface via Mantine notifications, per the parent Phase 0 spec's error-handling section.

### Mobile

- `AppShell` navbar collapses off-canvas below `sm`, burger toggle in the header.
- Stat tiles / source-health cards use `SimpleGrid` responsive column counts — no card-list-vs-table fallback needed here (that requirement applies to future pages with actual dense tabular data, e.g. Channels).

## Testing

- RTL: `AuthGate` (loading → authenticated; loading → redirect-to-login), `LoginPage` (submit success/failure), `StatTile` / `SourceHealthCard` (pure rendering), `DashboardPage` (mocked `apiClient`, including the partial-failure case).
- Manual verification against the real instance for actual end-to-end proof (login → Dashboard shows real counts and source status) — same pattern as Foundation's Task 11.

## Error handling

- Login failure: inline form error, not a full-page error.
- Dashboard section failure: scoped `Alert` per failed section, page stays usable.
- Session expiry while on Dashboard: silent-refresh-then-redirect via `AuthGate`, no user-facing error unless refresh itself fails (then redirect to `/login`, same as a fresh unauthenticated visit).
